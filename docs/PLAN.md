| Вопрос | Решение |

| Источник правил | Дмитрий; спорные места фиксируются как явные допущения |
| Мультитенантность | закладывается с первого дня, включается позже |

### Согласованные правила расчёта

| Правило | Решение |
|---|---|
| Курс валюты для счетов Zoho | референсный курс ЕЦБ на последний день месяца |
| Знак возвратов и возмещений | **всегда отрицательный**, единое правило для всех каналов |
| Allegro, продажи в EUR | страна получения — SK, ставка 20 %, UNION-OSS |
| Shopify, страна отправления | всегда ES — подтверждено |
| Shopify, заказы в Швейцарию | не попадают в отчёт, отдельной пометки не выводим |
| Семь SKU-коннекторов | по-прежнему исключаются из счетов Zoho; список редактируется в настройках |
| Строки «требует внимания» | только отображаются; исправление — правка исходного файла и повторная загрузка |
| История изменений справочников | не ведём, достаточно текущих значений |

Единое правило знака для возвратов — это изменение относительно legacy: там Allegro делает
возвраты отрицательными, а код Cdiscount берёт сумму по модулю. При сверке с эталонными
отчётами расхождения по знаку у Cdiscount будут ожидаемыми.

## 2. Четыре принципа, на которых всё держится

### 2.1. Система про транзакции, а не про файлы

Legacy оперирует файлами: загрузили → положили в папку → сгенерировали отчёт напрямую из файла.
Отсюда его болезни — двойной учёт при перекрывающихся выгрузках, отсутствие связи между
цифрой в отчёте и исходной строкой, невозможность что-либо проверить.

Новая система разбирает файл в **нормализованный журнал транзакций**, а отчёты строит как
проекции поверх журнала.

**Единица дедупликации — срез, а не строка.** Первая редакция плана предполагала построчный
внешний ключ. Проверка на реальных выгрузках за июль 2026 эту идею не подтвердила:

| Канал | Кандидат в ключ | Результат |
|---|---|---|
| Allegro | `identyfikator` | уникален (39 из 39) |
| Shopify | `Id` + `Lineitem sku` | уникален (72 из 72); один `Id` — на заказ, строк — по числу позиций |
| Amazon VAT | `TRANSACTION_EVENT_ID` + `ACTIVITY_TRANSACTION_ID` | **90 дублей** на 4188 строк; даже с `SELLER_SKU` и типом остаётся 16 |
| Cdiscount | `Invoice/Refund Id` | **54 дубля** на 109 строк — половина файла |
| Amazon Monthly | `Abrechnungsnummer` + `Bestellnummer` + `SKU` + дата + тип | **6 дублей** на 420 строк |

Причём часть дублей законна: две одинаковые строки `FC_TRANSFER` в один момент времени — это
действительно две разные перемещённые единицы, а не ошибка выгрузки. Искусственно доклеивать
к ключу номер строки нельзя: при повторной загрузке исправленного файла сдвиг на одну строку
переименует все последующие транзакции и создаст дубли вместо обновления.

Поэтому дедупликация идёт по срезу **(тенант, набор данных, страна, период)**. Повторная загрузка
файла за тот же срез замещает ранее загруженные транзакции этого среза целиком: старые помечаются
как вытесненные, новые вставляются. Построчного сопоставления между версиями файла нет.

Это корректно именно потому, что классификатор не принимает произвольные диапазоны дат — только
целый месяц либо целый календарный квартал (см. §4.3 разбора). То есть срезы не пересекаются
частично: они либо совпадают, либо не связаны.

Естественные ключи каналов всё равно сохраняем — но как обычный неуникальный индекс, для поиска
и drill-down, а не для дедупликации.

Даёт: идемпотентную повторную загрузку, безопасную перезаливку исправленного файла, drill-down
из любой цифры отчёта в исходную строку исходного файла, воспроизводимую перегенерацию.

### 2.2. Воспроизводимость

Перегенерация отчёта за тот же период на тех же данных обязана дать тот же результат.

- Курсы валют — **референсные курсы ЕЦБ** на конкретную дату, а не `GOOGLEFINANCE` «сейчас».
  Использованный курс сохраняется вместе с отчётом: значение, дата, источник.
- Деньги — `numeric(18,6)` в БД, `decimal.js` в приложении. Ни одного `float`.
- Отчёт — снапшот с зафиксированными входными данными, правилами и курсами.

### 2.3. Правила — данные, а не константы

Ставки НДС (с периодами действия), VAT-номера юрлиц, маппинг SKU, правила каналов, список
игнорируемых SKU — всё в БД и редактируется в UI. Это и снимает зависимость от разработчика,
и делает возможной мультитенантность: тенант — это набор своих правил.

### 2.4. `tenant_id` с первого дня

На всех таблицах, даже пока клиент один. Ретрофит тенантности в работающую бухгалтерию —
дорогая и опасная операция.

## 3. Архитектура

```
┌─────────────────────────── Next.js на Vercel ───────────────────────────┐
│                                                                         │
│  UI (Ant Design)              Server Actions / Route Handlers           │
│  ├── Загрузки                 ├── приём файла → Blob                    │
│  ├── Транзакции               ├── парсинг + классификация               │
│  ├── Отчёты                   ├── нормализация → журнал                 │
│  ├── Справочники              ├── генерация отчёта                      │
│  └── Настройки                └── выгрузка на Drive                     │
│                                                                         │
└────────┬──────────────────┬───────────────────┬─────────────────────────┘
         │                  │                   │
    ┌────▼─────┐      ┌─────▼──────┐     ┌──────▼────────┐
    │ Postgres │      │Vercel Blob │     │ Внешние API   │
    │ (Neon)   │      │ исходники  │     │ ├ Google Drive│
    │          │      │ + артефакты│     │ └ ЕЦБ (курсы) │
    └──────────┘      └────────────┘     └───────────────┘
```

Фоновой очереди в MVP нет: объёмы (≈4 тыс. строк на самый крупный отчёт) обрабатываются за
секунды. Но генерация оформляется как **задача с состоянием** (`report_run`) — ради аудита и
чтобы вынести её в очередь без переделки, когда появится Amazon SP-API.

## 4. Модель данных

Черновик; уточняется на этапе 0.

```
── Тенантность и доступ ──────────────────────────────────────
tenant            id, name, created_at
user              id, email, name
membership        tenant_id, user_id, role (owner|accountant|viewer)
google_connection tenant_id, google_account_email, refresh_token(enc),
                  root_folder_id, connected_at, status

── Периоды ───────────────────────────────────────────────────
period            id, tenant_id,
                  label ('2026.07 July' | '2026.Q3' | '2026.Y'),
                  granularity (month|quarter|year),
                  start_date date, end_date date,
                  status (open|closed),
                  origin (schedule|upload|manual),
                  created_at, closed_at, closed_by
                  UNIQUE (tenant_id, label)
                  INDEX (tenant_id, start_date)   ← порядок по дате, не по метке

Период существует до того, как в него что-то загрузили: первого числа
календарь открывает месяц, и чек-лист по нему виден пустым, а не отсутствует.
Квартал и год собираются из входящих в них месяцев — своих загрузок у них нет.

Расписание — строки channel_rule канала `periods`, рядом с настройками
отчётов в канале `reports`:

    periods/schedule  { month, quarter, year, fiscalYearStartMonth }
    periods/anchor    { month: '2026-08-01', quarter: '2026-07-01', … }

`anchor` — точка, с которой гранулярность начали заводить. Только вперёд:
включение кварталов в ноябре открывает Q4 и никогда не выдумывает Q1. Год
сдвигается вместе с `fiscalYearStartMonth`, кварталы остаются календарными —
их читает классификатор из содержимого файла.

Открытие идемпотентно: уникальность (tenant_id, label) делает догоняющий
запуск и вовремя сработавший одной и той же операцией. Поэтому вызывать можно
и из крона, и из загрузки страницы.

Периодичность отчётов — два разных вопроса, которые нельзя смешивать:
`definition.granularity` говорит, что умеет математика модуля, а
`granularities` в настройках отчёта (channel_rule `reports/<id>`) — что клиент
сдаёт. Отчёт предлагается на пересечении.

Отбор загрузок для периода: файлы берутся по перекрываемым датам, а не по
совпадению метки — у квартала и года своих файлов нет. Внутри среза
(канал + страна) побеждает более крупный файл, мелкие закрывают оставшиеся
дыры. Иначе канал, приславший и квартальный экспорт, и три месячных, был бы
посчитан дважды.

Незавершённый период не строится: квартал из двух прошедших месяцев выглядит
как квартал и им не является.

── Приём файлов ──────────────────────────────────────────────
source_file       id, tenant_id, original_filename, mime, size_bytes,
                  sha256, blob_key, uploaded_by, uploaded_at,
                  source_type, country_code,
                  period_id → period,
                  period_label ('2026.07 July' | '2026.Q3'),
                  period_start date, period_end date,
                  period_granularity (month|quarter),
                  header_row_index, detection_meta jsonb,
                  status (received|classified|parsed|superseded|rejected),
                  superseded_by_file_id, reject_code, reject_message
                  UNIQUE (tenant_id, sha256)

── Журнал транзакций ─────────────────────────────────────────
transaction       id, tenant_id, source_file_id, source_row_number,
                  dataset (amazon_vat|amazon_monthly|allegro|cdiscount|shopify),
                  channel, country_code,
                  period_label, period_start, period_end,   ← наследуются от файла
                  natural_key text,                          ← неуникальный, для поиска
                  occurred_on date, transaction_type,
                  currency, gross numeric, vat_amount numeric,
                  net_amount numeric, vat_rate numeric,
                  departure_country, arrival_country,
                  seller_vat_number, buyer_vat_number, tax_scheme,
                  sku, quantity numeric,
                  needs_attention bool, attention_reason,
                  is_current bool,                           ← false у вытесненных
                  raw jsonb
                  INDEX (tenant_id, dataset, country_code, period_start, is_current)
                  INDEX (tenant_id, natural_key)

── Справочники (редактируются в UI) ──────────────────────────
vat_rate          tenant_id, country, rate, valid_from, valid_to
seller_vat_number tenant_id, country, vat_number, valid_from, valid_to
sku_mapping       tenant_id, channel, source_sku, target_sku,
                  item_name, is_ignored
channel_rule      tenant_id, channel, key, value jsonb, note
fx_rate           rate_date, base, quote, rate, source   (кэш ЕЦБ)

── Отчёты ────────────────────────────────────────────────────
report_run        id, tenant_id, report_type, period_id → period, period,
                  status (queued|running|succeeded|failed),
                  requested_by, started_at, finished_at,
                  error_message,
                  fx_snapshot jsonb, rules_snapshot jsonb,
                  stats jsonb (обработано/пропущено/строк)
report_run_source report_run_id, source_file_id
report_artifact   id, report_run_id, kind (xlsx|gsheet),
                  filename, blob_key,
                  drive_file_id, drive_url,
                  drive_status (pending|synced|failed), drive_synced_at

── Аудит ─────────────────────────────────────────────────────
audit_log         tenant_id, user_id, action, entity, entity_id,
                  payload jsonb, created_at
```

Карточка отчёта в реестре собирается из `report_run` + `report_run_source` + `report_artifact`:
тип, период, дата генерации, перечень использованных источников, кнопка скачивания,
ссылка на Google Drive.

### Как отчёт выбирает транзакции

Отбор идёт **по периоду, присвоенному файлу при загрузке** (`period_label`), а не по дате
отдельной транзакции (`occurred_on`), и только среди `is_current = true`.

Это сознательный выбор. Legacy подбирает источники ровно так же — точным совпадением
Type + Period в реестре, — и любое отклонение здесь сломает сверку с эталонными отчётами.
Побочное следствие: отчёт за месяц нельзя собрать из файла, классифицированного как квартал,
и наоборот. Ровно как сейчас. `occurred_on` при этом хранится и индексируется — когда
понадобится гибкость, она добавляется без миграции данных.

## 5. Этапы

Оценка сложности: **S** — простой, **M** — средний, **L** — крупный.

### Этап 0. Фундамент — **M**

- Прочитать документацию Next.js 16, которая лежит в `node_modules/next/dist/docs`
  (обязательное требование `AGENTS.md`: в этой версии есть ломающие изменения).
- Ant Design v5 + `@ant-design/nextjs-registry` (иначе мигают стили при SSR), тема, тёмный режим.
- Postgres (Neon) + Drizzle ORM + миграции.
- Аутентификация (Auth.js), таблицы `tenant` / `user` / `membership`, посев одного тенанта.
- Vercel Blob.
- Шифрование секретов (refresh-токен Google): AES-GCM, ключ из переменной окружения
  `ENCRYPTION_KEY`, отдельной от ключа сессий.
- Каркас интерфейса: сайдбар, страницы-заглушки, обработка ошибок, пустые состояния.
- Vitest + структура для golden-тестов.

**Готово, когда:** приложение задеплоено на Vercel, вход работает, миграции применяются, пустой каркас доступен по домену.

### Этап 1. Приём и распознавание файлов — **L**

- Загрузка **напрямую в Blob с клиента** (`@vercel/blob/client`, `handleUpload`). Через обычный
  Server Action нельзя: лимит тела запроса у функций Vercel — 4.5 МБ, а файлы допускаются до 20 МБ.
- Парсеры: CSV (определение кодировки с фолбэком на Windows-1252, определение разделителя, BOM)
  и XLSX.
- **Старый бинарный `.xls` не поддерживаем.** `exceljs` его не читает, а в корпусе из 98 выгрузок
  за 2025–2026 нет ни одного: 42 CSV и 56 XLSX. Отклоняем с внятным сообщением и просьбой
  пересохранить. Если формат когда-нибудь появится — добавляется отдельной библиотекой.
- Классификатор: порт логики из [Classifier.gs](legacy-gas/scripts/Classifier.gs) —
  4 простых типа по обязательным заголовкам + семейство Amazon Monthly
  (9 языковых профилей, страна по домену маркетплейса).
- Определение периода: 5 разных стратегий, месяц или полный квартал.
- **Правило дат:** берётся календарная дата так, как она записана в источнике, без пересчёта
  часового пояса, и хранится как `date`. Legacy поступает так же, и это принципиально: пересчёт
  `2026-07-31 22:34:13 +0300` в UTC увёл бы транзакцию в предыдущий месяц.
- Дедупликация по `sha256` — повторная загрузка того же файла отклоняется с внятным сообщением.
- Экран «Загрузки»: список, статус, определённый тип и период, причина отказа, превью первых строк.
- Подготовка обезличенных фикстур для golden-тестов (см. §10): скрипт замены имён, email, адресов
  и телефонов на синтетические при сохранении сумм и структуры.
- **Улучшение против legacy:** период Amazon Monthly определять не только по имени файла,
  но и по данным внутри (fallback), с возможностью подтвердить вручную.

**Готово, когда:** все **98 исходных выгрузок** из `exported-reports` (42 CSV + 56 XLSX; папка
`Reports` не в счёт — это результаты работы генераторов) классифицируются корректно, и ни одна не
уходит в «не распознано» ошибочно.

> Про парные файлы Cdiscount вида `… July.xlsx` и `… July(1).xlsx`: это не две разные выгрузки.
> В папке Drive лежат и оригинал, и его конвертированная копия в виде Google Sheet; при скачивании
> обоих браузер добавил суффикс. Содержимое совпадает (112 строк), различается сериализация: в
> оригинале даты строками, в копии — датами. Для фикстур берём файлы без `(1)`.

### Этап 2. Нормализованный журнал транзакций — **L**

- Мапперы по каналам: файл → `transaction[]`, с корректным разбором чисел по локали
  (**здесь чинится баг с Unit Price = 0**: числа парсятся при импорте и хранятся как `numeric`,
  никаких формул в таблицах).
- Единая функция разбора чисел вместо пяти разных, как в legacy.
- Дедупликация по срезу `(tenant_id, dataset, country_code, period_start)`: загрузка нового файла
  за тот же срез помечает прежние транзакции `is_current = false`, а файл — `superseded`.
  Ничего не удаляется физически, история загрузок остаётся видимой.
- Пометка `needs_attention` вместо жёлтой заливки ячеек (например, не удалось определить ставку НДС).
  Только отображение и фильтр — правка значений в UI не делается, исправляется исходный файл.
- Единое правило знака: возвраты и возмещения записываются отрицательными во всех каналах.
- Экран «Транзакции»: фильтры по каналу, периоду, типу, стране, статусу; drill-down в исходную строку.

**Готово, когда:** для каждого исходного файла сумма и количество строк в журнале сходятся с
исходником; повторная загрузка того же среза не создаёт дублей и не теряет данные; отчёт,
собранный до и после перезаливки идентичного файла, совпадает.

### Этап 3. Справочники и курсы — **M**

- CRUD ставок НДС по странам с периодами действия. Периоды действия нужны для корректного
  пересчёта прошлых месяцев и к аудиту изменений отношения не имеют — их оставляем.
- CRUD VAT-номеров юрлиц.
- CRUD маппинга SKU и списка игнорируемых SKU.
- Правила каналов (страна отправления, соответствие валюты и страны у Allegro, обработка CH и GB
  у Shopify) — вынести из кода в настройки.
- Загрузка курсов ЕЦБ (ежедневный XML-фид), кэш в `fx_rate`; для счетов Zoho берётся курс на
  последний день отчётного месяца.
- Без версионирования и журнала правок справочников — хранятся только текущие значения.
- Первичное наполнение справочников значениями из legacy.

**Готово, когда:** ни одно бизнес-правило из §5 [ANALYSIS.md](legacy-gas/ANALYSIS.md) не захардкожено в коде.

### Этап 4. Генераторы отчётов — **L**

Каждый генератор — чистая функция «журнал + правила + период → строки отчёта», без побочных
эффектов, покрытая тестами.

1. **Sales report by currency** — разрезка Amazon VAT по `TRANSACTION_CURRENCY_CODE` с итогами. **S**
2. **Off-Amazon Sales** — нормализация Allegro + Cdiscount + Shopify в 13 колонок. **M**
   Правила по каналам расписаны в §5.2 разбора.
3. **Amazon invoice for Zoho** — агрегация 10 стран по SKU + цена, маппинг в номенклатуру Zoho,
   курс ЕЦБ на последний день месяца. **M**

Плюс `report_run` как задача со статусом, снапшоты правил и курсов, откат при ошибке.

**Готово, когда:** golden-тесты на парах «вход → выход» из `exported-reports` проходят.
Каждое расхождение с эталоном разобрано и классифицировано: наша ошибка либо баг legacy.
Второе фиксируется в `docs/known-deviations.md` — по одной записи на расхождение: отчёт, период,
в чём разница, сумма влияния, почему считаем правильным наш вариант. Этот документ идёт клиенту
как обоснование перехода.

Уже известные ожидаемые расхождения: нулевые `Item Price` в счетах Zoho по восьми странам,
знак возвратов у Cdiscount.

### Этап 5. Выдача результата — **M**

- Реестр отчётов: строка = тип, период, дата генерации, источники, статус, скачать, ссылка на Drive.
- Генерация XLSX (`exceljs`) с форматами, близкими к текущим.
- Подключение Google-аккаунта: OAuth со скоупом `drive.file`, хранение refresh-токена в
  зашифрованном виде, экран «Интеграции» со статусом подключения.
- Выгрузка отчёта на Drive как Google Sheets, в папку `<Тип> - <Период>`, сохранение
  `drive_file_id` и ссылки.
- **Скоуп `drive.file` и выбор папки.** Приложение видит только те файлы и папки, которые само
  создало **либо которые пользователь указал явно через Google Picker**. Первая редакция плана
  утверждала, что дать клиенту выбрать существующую папку невозможно и придётся создавать свою —
  это оказалось неверно: Picker для того и существует, выбор через него выдаёт приложению доступ
  к указанной папке. Реализовано так: клиент подключает аккаунт, затем выбирает папку в обычном
  окне Google. Введённый руками идентификатор папки не подошёл бы — он не несёт разрешения.
  Чувствительный скоуп `drive` и верификация приложения в Google не нужны.
- Отдельный статус синхронизации с Drive и кнопка «повторить» — недоступность Drive не ломает
  генерацию.

**Готово, когда:** клиент находит отчёт и в приложении, и у себя на Google Drive; отключение Drive не мешает работать.

### Этап 6. Полировка и передача — **M**

- Роли (владелец / бухгалтер / наблюдатель).
- Аудит-лог: кто что загрузил, сгенерировал, изменил в справочниках.
- Проверка на реальном месяце вместе с клиентом, сверка цифр.
- Документ «Правила и допущения» — итоговый, согласованный.
- Домен, бэкапы БД, мониторинг ошибок.

| Зона | Выбор | Почему |
|---|---|---|

| Хранилище | Vercel Blob | в одном контуре с приложением |
| Аутентификация | Auth.js (NextAuth v5) | |

## 7. Риски

| Риск | Оценка | Что делаем |
|---|---|---|
| Логика VAT Regular/OSS утеряна | высокий | вне MVP; параллельно ищем файлы в редакторе Apps Script |
| Расхождения с эталонными отчётами из-за багов legacy | средний | реестр расхождений, каждое разбирается явно; в спорных верим бухгалтерии, а не legacy |
| Правила каналов изменятся | низкий | согласованы (§1) и вынесены в настройки — меняются без разработчика |
| Формат выгрузок маркетплейсов изменится | средний | классификатор на данных, а не на позициях колонок; внятная диагностика при отказе |
| Квоты и лимиты Google Drive API | низкий | выгрузка асинхронная, с ретраями и статусом |
| Рост объёмов | низкий | генерация уже оформлена как задача, выносится в очередь без переделки |

## 8. Что сознательно не входит в MVP

- Разбор Amazon VAT на Regular / OSS / Exceptions и подготовка VAT-декларации.
- Интеграции с API маркетплейсов (Amazon SP-API, Shopify API).
- Отправка счетов в Zoho Books через API — только выгрузка файла.
- Самостоятельная регистрация пользователей, тарифы, биллинг.
- Зеркалирование исходных файлов на Google Drive.
- Редактирование проблемных транзакций прямо в интерфейсе.
- Журнал изменений справочников.

## 9. Открытые вопросы

Все расчётные правила согласованы (см. §1). Остаётся одно:

1. Найдутся ли `RegularSheet.gs` / `OssSheet.gs` во втором проекте Apps Script?
   Нужно открыть таблицу с меню «Amazon VAT» → Расширения → Apps Script и посмотреть список
   файлов слева. От этого зависит объём второго этапа, но не MVP.

Отдельно отмечу два следствия принятых решений — не возражение, а то, что стоит держать в голове:

- Швейцарские заказы Shopify и семь SKU-коннекторов не попадают в отчёты, но **попадают в журнал
  транзакций** — импорт и генерация отчётов разделены. То есть данные не теряются и в любой
  момент находятся фильтром, даже без отдельного блока в отчёте. Это ничего не стоит и включено
  по умолчанию.
- Строки `needs_attention` правятся в исходном файле и загружаются заново. Замещение по срезу
  (§2.1) делает такую перезаливку безопасной: прежняя версия среза целиком уходит в историю,
  дубли не появляются.

## 10. Отдельно: персональные данные

В `docs/legacy-gas/exported-reports` лежат реальные данные покупателей — в выгрузках Shopify
есть `Email`, `Billing Name`, адреса и телефоны, в отчётах Amazon — `BUYER_NAME` и
`ARRIVAL_ADDRESS`. Это персональные данные граждан ЕС, к которым применяется GDPR.

**Сделано:** `docs/legacy-gas/exported-reports/` добавлена в `.gitignore` до первого коммита, так
что в историю репозитория эти данные не попадут. Файлы остаются на диске и доступны для работы.

Для golden-тестов используются обезличенные выборки: имена, email, адреса и телефоны заменяются
на синтетические, суммы и структура сохраняются. Скрипт обезличивания — задача этапа 1;
результат его работы коммитить можно и нужно, иначе тесты не воспроизводятся на другой машине.
