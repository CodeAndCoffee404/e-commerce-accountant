# Как расширять систему

Ответ на вопрос «отключать существующее можно, а как добавлять новое?».

## Что меняется без кода, прямо в приложении

| Что | Где |
| --- | --- |
| Включить/выключить отчёт | Settings → Reports |
| Канал или маркетплейс обязателен / опционален | Settings → Reports |
| Ставки VAT (с датой вступления) | Settings → VAT rates |
| Сам НДС-номер юрлица и срок его действия | Settings → Seller VAT |
| Маппинг и игнор SKU | Settings → SKU mapping |
| Типы операций каналов, валютные правила, дефолты | Settings → Channel rules |
| Кто имеет доступ и с какой ролью | Settings → Team |

Правило разделения: **конфигурация — это то, что меняет параметры расчёта,
код — то, что меняет его смысл.** Расчётная математика намеренно не собирается
конструктором в интерфейсе: у отчёта бухгалтерская цена ошибки, и каждый
генератор при добавлении сверяется с эталоном построчно. Конструктор отчётов
дал бы гибкость ценой именно той гарантии, ради которой всё строилось.

## Архитектура: модули над общим ядром

```
Channel modules  →  нормализованный журнал транзакций  →  Report modules
(src/modules/channels)                                    (src/modules/reports)
```

Ядро — загрузка, хранение, права, статусы, запуск — итерирует **реестры**
(`registry.ts` в каждой папке) и не знает модулей по именам. Контракты
стандартные и узкие:

- **Channel module** (`src/modules/channels/<канал>.ts`): один файл, внутри
  которого профиль распознавания, `classify(grid, filename)`, маппер
  «сырая строка → транзакция» и дефолтные правила канала.
- **Report module** (`src/modules/reports/<отчёт>.ts`): определение (что
  читает, что требует, тексты) + `generate(rows, context)` → листы, плюс
  необязательный `validate` — собственная проверка полноты (так инвойс Zoho
  требует свои десять маркетплейсов, и ядро об этом не знает).

Добавление нового — **extension, не modification**: новый файл + строка в
реестре. Уже отлаженный модуль не может быть сломан чужим изменением, потому
что никто, кроме реестра, на него не ссылается. Эквивалентность после
переезда на эту структуру доказана корпусом из 98 реальных выгрузок и
golden-тестами — байт в байт.

## Добавить новый отчёт (~день работы)

1. **Миграция**: новое значение в enum `report_type` (одна строка,
   `drizzle-kit generate`).
2. **Модуль** `src/modules/reports/<имя>.ts`: определение + генератор в одном
   файле. Вход — строки журнала + правила + курсы, выход — листы. Деньги
   только через `decimal.js`.
3. **Строка в реестре** `src/modules/reports/registry.ts`.
4. **Golden-тест**: собрать из реальных выгрузок, сверить с образцом
   (`tests/golden/`).

Карточка на Reports, доступность периодов, чеклист дашборда, вкл/выкл и
required/optional в настройках, снапшоты — всё подхватывается из определения.

## Добавить новый канал продаж (~1–2 дня)

Например, клиент начал продавать на Kaufland.

1. **Миграция**: значение в enum `dataset_id` (одна строка).
2. **Модуль** `src/modules/channels/kaufland.ts`: профиль (обязательные
   заголовки, откуда период), `classify` через готовый тулкит, маппер
   (непрочитанное число — флаг `needsAttention`, никогда не ноль молча),
   дефолтные правила. Файл опознаётся по содержимому, не по имени.
3. **Строка в реестре** `src/modules/channels/registry.ts`. «Restore missing
   defaults» доставит правила существующим арендаторам.
4. **Подключить к отчёту**: датасет в `datasets` нужного модуля отчёта.
5. **Фикстуры**: `npm run fixtures -- "<файл>"` анонимизирует реальный
   экспорт; тесты классификации и маппинга по образцу существующих.

Дашборд, загрузки, сверка «файл → журнал», замещение при перезаливке — ядро
не знает названий каналов, всё заработает само.

Пошаговый вариант этого раздела для Claude Code — скилл
[`add-upload-type`](../.claude/skills/add-upload-type/SKILL.md): те же шаги,
но с точными путями файлов, порядком правок и командами для валидации. При
изменении этого раздела стоит свериться и с ним, чтобы они не разошлись.

## Добавить страну Amazon

Профиль языка уже может существовать (английский обслуживает UK и IE).
Если язык новый — профиль заголовков в `AMAZON_MONTHLY_PROFILES`, домен в
`AMAZON_MARKETPLACE_DOMAINS`, страна в `ZOHO_COUNTRIES` и ставка VAT в seed.

## Добавить страницу, маршрут или Server Action

Данные каждой компании отделены колонкой `tenant_id`, и **это проверяет сама
Postgres**: у всех таблиц с этой колонкой включена row-level security, а запрос,
который не назвал компанию, получает **ноль строк**, а не чужие. Забытый
фильтр перестал быть утечкой и стал пустым экраном.

Компания называется один раз на единицу работы, внутри транзакции — иначе
нельзя: соединение идёт через пулер Neon, и сессионная настройка утекла бы на
чужой запрос.

Отсюда форма, одинаковая у всех точек входа:

```ts
export async function saveVatRate(input: unknown): Promise<ActionResult> {
  return inRequest(() => saveVatRateInScope(input));
}

async function saveVatRateInScope(input: unknown): Promise<ActionResult> {
  // ...настоящая работа, как и была
}
```

Экспортируемая функция — дверь в одну строку, работа лежит рядом, в функции с
тем же именем и окончанием `InScope`. Так же устроены страницы, layout и
маршруты в `src/app/api`. `inRequest` сам читает сессию: компания неизвестна,
пока сессия не прочитана, а обернуть себя изнутри функция не может.

Исключение одно — ночной cron: он честно обходит все компании и пишет это прямо,
`acrossTenants()` для списка и `withTenant(id, …)` на каждую. `acrossTenants()`
— единственная дверь мимо проверки базы (вход в систему, cron, тесты) и
намеренно отказывается открываться внутри области видимости компании: это
направление и есть форма утечки.

Проверяет это `tests/tenant-scope-coverage.test.ts`: он обходит все страницы,
маршруты и Server Actions и падает на двери, которая забыла открыться.
Исключения перечислены в самом тесте, каждое с причиной. А
`tests/tenant-isolation.test.ts` проверяет саму изоляцию — снаружи области
видимости, там же, где был бы настоящий забытый фильтр.

### Миграция, которая трогает данные

**Первым оператором ставьте обход**, иначе миграция обновит ноль строк и
отчитается успехом:

```sql
SELECT set_config('app.bypass_rls', 'on', true);--> statement-breakpoint
UPDATE "transactions" SET ... ;
```

Это проверено: без этой строки `UPDATE` возвращает `UPDATE 0`, деплой проходит,
данные остаются старыми.

### Чистая база не поднимается одной миграцией

Проверено 2026-09-04: `drizzle-kit migrate` и программный мигратор прогоняют
**все неприменённые миграции в одной транзакции**, а одна из ранних добавляет
значение в enum `report_type` и тут же им пользуется. Postgres это запрещает в
пределах одной транзакции, поэтому цепочка с нуля падает на
`unsafe use of new value "custom_slice"`.

На боевой и dev-базах этого не видно: там миграции применялись по мере
появления, разными деплоями. Но новое окружение с нуля так не поднять. Когда
понадобится — разнести добавление значения и его использование по разным
миграциям.

### Новая таблица с колонкой компании

Добавьте `tenantIsolation()` в её список в `schema.ts` и **допишите руками**
`ALTER TABLE ... FORCE ROW LEVEL SECURITY;` в сгенерированную миграцию:
drizzle-kit этого не умеет, а без `FORCE` политика не действует на владельца
таблиц — то есть на роль, под которой ходит приложение. Забыть нельзя:
`tests/tenant-isolation.test.ts` выводит список таблиц из самой схемы и падает
на той, у которой `FORCE` нет.

## Добавить компанию

Система обслуживает несколько компаний. У каждой свои загрузки, отчёты и
настройки, и одна не видит другую — это проверяет сама Postgres, а не код (см.
выше).

`/admin`, доступна супер-админу: название и адрес первого владельца. Компания
заводится вместе со своими справочниками — пустая таблица ставок дала бы отчёт,
который собирается и ничего не считает.

**Компанию опознаёт её идентификатор**, `tenants.id`. На него смотрят все её
строки, папка её файлов в хранилище и список доступа. Название — просто
подпись: его меняет владелец компании в «Настройки → Компания», оно не
уникально, и две компании с одинаковым именем — это две компании.

### Правила, по которым считаются отчёты

`src/modules/companies/` хранит значения, из которых считаются отчёты: где
отгружается товар, что считается продажей, какие рынки получают отдельную
строку НДС, как называются счета в Zoho, чем заполняются справочники в первый
день.

Почему это код, а не настройки: `docs/RULES.md` объясняет, что экран, где можно
поменять страну отгрузки или «что считается продажей», — это экран, на котором
гарантийная отправка тихо становится выручкой. Меняется пул-реквестом с ревью и
golden-тестом.

**Сегодня набор один, и его получают все компании.** `rulesFor(идентификатор)`
принимает идентификатор и игнорирует его — это шов, а не небрежность: в день,
когда второй компании понадобятся свои ответы, меняется эта функция и больше
ничего. В базе не хранится ничего, что говорило бы, какие правила у компании;
такая колонка была бы вторым идентификатором для того, у чего он уже есть.

Из этого следует то, что надо знать до появления второй компании: **она получит
имена счетов Geyser в Zoho и его нумерацию счетов**. Пока правила общие, вторую
компанию заводить нельзя. Что нужно от клиента, чтобы это исправить:

- **какие каналы** — Shopify, Amazon, Allegro, Cdiscount;
- для Shopify — **страна отгрузки**, какой из датасетов её магазин, какие
  страны получают свою строку НДС;
- **названия счетов учёта в Zoho** — байт в байт: счёт товаров, имя покупателя,
  префикс номера счёта. Zoho читает имя как ссылку в справочник, и файл с чужим
  именем не импортируется целиком.

НДС-регистрации входят в него наполовину. Пара «страна + схема», по которой
отчёт ищет номер, — правило: она следует из того, какие отчёты компания считает.
Сам номер и срок его действия — факт самой компании, и вводятся на экране
«Настройки → Seller VAT». Пара показана там подписью строки: менять её нельзя,
а видеть нужно.

Сид номера **не выдаёт**: у новой компании регистраций нет вовсе, и её первый
отчёт откажется собираться, назвав недостающие. Это лучше, чем файл с чужими
номерами, который выглядит исправным — но только при условии, что регистрацию
можно завести. Какое-то время было нельзя: сид перестал их выдавать, а кнопки
«добавить» не было, и сообщение об ошибке предлагало сделать то, чего экран не
умел. Кнопка есть (`createSellerVatNumber`); если она когда-нибудь снова
исчезнет, вместе с ней исчезнет и возможность построить первый отчёт.

Поэтому на том экране нет ни «добавить», ни «удалить»: исправить номер и
закрыть регистрацию датой можно, а завести пятую страну — нельзя, это правка
кода. Действие на сервере страну и схему из браузера не принимает вовсе.
Принимало раньше, и тогда правка, сделанная ради заметки, могла сменить схему
у OSS-регистрации и молча выкинуть все экспортные продажи из Off-Amazon
Sales.

### Закрыть компанию и удалить её

**Закрытая компания только читается.** Её люди входят и смотрят то, что уже
есть; ничего не загружается, не собирается и не меняется, а ночная задача
проходит мимо. Пропущенные месяцы откроются сами при первом прогоне после
открытия — задача спрашивает, что должно быть открыто, а не что следующее.

Запрет ставит Postgres, а не проверка в коде: область закрытой компании
открывает транзакцию в режиме `transaction_read_only`, и тогда любой INSERT,
UPDATE и DELETE в ней отказывает независимо от того, что забыли проверить
выше (`closeToWrites` в `src/lib/db/tenant.ts`). Проверка в правах доступа тоже
есть, но она нужна лишь для того, чтобы кнопки гасли заранее, а не чтобы
запрет работал.

Режим односторонний: Postgres не возвращает транзакцию в режим записи после
первого же запроса. Поэтому он ставится только на транзакции, которую область
открыла сама. Вложенный случай — вход в систему, шаг супер-админа внутрь
компании, ночная задача — идёт по чужой транзакции, которой запись нужна.

**Удалить можно только закрытую компанию, и с вводом названия.** Два решения в
разные моменты, потому что в списке компаний соседняя строка в одном пикселе.
Строки уходят по внешним ключам, а ключи файлов в хранилище приходится
прочитать заранее: после удаления строк уже ничто не знает, чьи это байты.

### Чего пока нет

- **Набор датасетов у отчёта статический.** `off_amazon_sales` и счёт Shopify
  объявляют `shopify_geyser` в своих определениях.
- **Часть констант Amazon остаётся общей**: список маркетплейсов, имена
  покупателей `Amazon <страна>`.
- **У Allegro страна отгрузки живёт в двух местах**: в правилах и в правиле
  канала `departure_country`. Обе говорят PL.
- **Список игнорируемых SKU подразумевает Amazon** — так он и засевается.

## Две попытки облегчить страницы, которые не сработали

Обе относятся к весу интерфейса и обе проверены на production-сборке. Записаны,
чтобы следующая попытка начиналась с этого места, а не с нуля.

### Статический CSS antd не собирается из двух тем

Идея верная: antd генерирует стили во время рендера, и Next вклеивает их в
каждый ответ — от 177 до 322 KB `<style>` на страницу, большая часть документа,
заново на каждый запрос. Правила при этом не меняются: тема выражена через CSS-
переменные (`cssVar`), правило компонента говорит `var(--ant-color-text)`, и
между светлой и тёмной различается только блок переменных.

Не выходит на `@ant-design/static-style-extract@2.1.0`: он **не соблюдает**
`cssVar.key`. Прогон для светлой темы и прогон для тёмной дают блоки переменных
под одним и тем же сгенерированным классом (`.css-var-_R_29n_`), то есть второй
перекрывает первый. Это ровно тот баг, из-за которого ключ и был заведён —
«тёмный layout, белые селекты», пойманный в проде на телефоне.

Чтобы это заработало, нужно переписывать имя класса в готовом CSS на свой
(`.css-var-light` / `.css-var-dark`), то есть опираться на внутреннее
соглашение об именах: сменится оно — приложение молча потеряет палитру. И
отдельно нужно решить, что делать с `AntdRegistry`: он и есть то, что вклеивает
стили, а без него первая отрисовка проходит без переменных.

### Ленивый чанк клиентского компонента не выпускается

Разделение диалога справки (кнопка в шапке — на каждой странице, страница текста
за ней — нет) дало на замере минус 458 KB сырого JS на `/reports`, около 20 %.
**Замер оказался ложным:** чанк, на который ссылается сборка, в неё не попадает
— `curl` отдаёт 500, в `.next/static/chunks/` файла нет, — а браузер получает
`ChunkLoadError`. Байты «сэкономлены» тем, что не приехали, а справка перестала
открываться.

Воспроизводится и через `next/dynamic` (с `ssr: false` и без), и через
`React.lazy` + `Suspense`, на трёх сборках. То есть дело не в механизме, а в
Next 16.3 с Turbopack. Пока это так, делить клиентские компоненты по чанкам
здесь нельзя, и любой замер веса после такого деления надо проверять тем, что
функция всё ещё работает.

## Чего не делать

- Не расширять маппер «почти подходящего» канала под новый — у двух каналов
  всегда расходится семантика возвратов или комиссий, и это вылезает через
  месяц в цифрах.
- Не добавлять отчёт без golden-теста. Совпадение с эталоном — единственное
  определение «правильно», которое здесь есть.

## Можно ли перенести это в само приложение?

Частично — да, и два конкретных инструмента построить реально. Ядро — нет,
и причины инженерные, не вкусовые.

### Что можно построить в приложении

**Конструктор сводного отчёта — был построен, затем убран из продукта.**
Четвёртый тип отчёта (`custom_slice`) существовал как «настраиваемый срез
журнала»: фильтры, группировки и суммы по фиксированному списку полей (канал,
страна, валюта, тип, SKU; период задавался при сборке). Определения
создавались на Settings → Custom reports, каждое получало свою карточку на
Reports и строилось как обычный отчёт — с записью запуска и снимком
определения. Функциональность и её данные полностью удалены. Устройство
осталось образцом обобщения: ядро сохранило понятие «отчёт с вариантами»
(`variants` в определении модуля), и любой будущий параметризуемый отчёт может
переиспользовать его без правок ядра.

**Мастер добавления CSV-канала.** Загрузил образец → сопоставил колонки
(дата, сумма, валюта, тип операции) → превью разобранных строк. Ключевое
условие, без которого его строить нельзя: профиль **не активируется, пока
итоги разбора не совпали с итогами из кабинета самого маркетплейса**, введёнными
руками. Это воспроизводит дисциплину golden-тестов внутри приложения — эталоном
служат цифры площадки. Подходит для простых каналов «строка = продажа».

### Почему ядро остаётся кодом

**1. Без эталона нет определения правильности.** Каждый из трёх отчётов
сверен построчно с отчётами, которые бухгалтер годами сдавал из legacy-скриптов.
Отчёт, собранный в конструкторе, сверять не с чем — «правильно» превращается в
«похоже на правду». Для информационного среза это приемлемо, для документа в
отчётность — нет.

**2. Обрыв выразительности.** В этом проекте *каждый* реальный канал и отчёт
содержал хотя бы одно правило, которое не выражается универсальным маппингом:
Shopify пишет строку на заказ, а не на позицию; у Cdiscount знак возврата в
legacy менялся от месяца к месяцу; Allegro мешает свои комиссии в ту же
выписку, что и продажи; инвойс Zoho нумеруется и датируется по своим
соглашениям. Конструктор, способный выразить такое, — это язык
программирования с интерфейсом хуже, чем у кода; конструктор без этого делает
только отчёты-игрушки.

**3. Ошибки в деньгах тихие.** Неверно сопоставленная колонка или неудачное
округление не падают с ошибкой — они дают правдоподобные цифры, которые
всплывают через месяцы. Код ловится тестами на 98 реальных файлах;
пользовательское определение не ловится ничем. (Именно поэтому мастер каналов
выше обусловлен принудительной сверкой итогов.)

**4. Издержки, если всё же делать.** Замена Postgres-enum'ов на текстовые
колонки (миграция), версионирование пользовательских определений при эволюции
схемы, разрешение коллизий классификатора между встроенными и
пользовательскими профилями, и поддержка: ошибка в определении, собранном
клиентом, неотличима от ошибки приложения.

### Практический итог

Пока клиент один, путь из этого документа быстрее и надёжнее любого мастера:
канал — 1–2 дня кодом со сверкой. Когда продукт станет мультитенантным SaaS,
мастер каналов со сверкой перейдёт из «можно» в «нужно» — длинный хвост чужих
магазинов иначе не обслужить. Архитектура к этому готова: профили распознавания
уже данные (`SIMPLE_DATASETS`), их переезд из кода в таблицу — механика, не
переделка.

## Сколько можно предусмотреть заранее?

Предугадать инстансы нельзя; предугадать форму — можно, и это сделано.

**Слой, где «всё в мире» уже предусмотрено — журнал.** Любая продажа любого
канала сводится к строке: когда, что, куда, почём, в какой валюте, с каким
налогом, из какого файла. Это форма предметной области, не наша гипотеза.
Поэтому ядро — журнал, периоды, замещение, сверка, отчёты-свёртки, закрытие
месяца — не меняется при появлении нового канала вообще.

**Слой, который непредсказуем принципиально — семантика канала.** Четыре
наших канала дали четыре сюрприза (строка-на-заказ у Shopify, плавающий знак
возврата у Cdiscount, комиссии в выписке продаж у Allegro, девять языков у
Amazon), и ни один не угадывался без реальных файлов. Писать мапперы «на
будущее» без выгрузок из реального аккаунта вредно: маппер-угадайка не падает,
а даёт правдоподобные неверные цифры. Иллюзия поддержки хуже её отсутствия.

**Правильная метрика готовности** — не «сколько каналов поддержано», а
«сколько стоит следующий». Здесь она константа и не растёт с размером системы:
канал — 1–2 дня от файла до сверенного, отчёт-свёртка — около дня. Отчёту,
которому нужны данные, которых в файлах нет (себестоимость, остатки), сначала
нужен новый вход — журнал знает только то, что каналы отдают.
